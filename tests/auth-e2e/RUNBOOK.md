# AUTH-006 — Isolated Authentication Security & Full-Loop E2E Gate

TASK-AUTH-006. Owner: QA / GLM. Branch: `task/auth-006-security-e2e`.

This directory is a self-contained Playwright gate that proves the integrated real behavior
of AUTH-003 (BFF session), AUTH-004 (backend Auth0 access-token verification), and
AUTH-005 (frontend session integration) against the **unmodified production build** of
both runtimes — plus the positive production secure-cookie proof (scenario I) on a real
HTTPS topology.

## One command = one clean run

From the repository root:

```bash
pnpm exec playwright test --config tests/auth-e2e/playwright.config.mts
```

A single invocation performs the full lifecycle:

1. `globalSetup` resolves a unique run id and asserts the port plan is free.
2. Creates an isolated PostgreSQL database `mystcrag_auth006_<runId>_test` (name pattern
   is asserted before any `CREATE`/`DROP`), runs `prisma migrate deploy` and the standard
   seed against it.
3. Prepares the **run-scoped build checkout**: `apps/backend` and `apps/frontend` are
   copied into `output/playwright/auth-006/<runId>/work/apps/` (node_modules and
   `packages/` symlinked to the frozen install) and every build/start afterwards runs
   INSIDE that copy. The developer workspace's `apps/frontend/.next` and
   `apps/backend/dist` are never read, written, or deleted — and no build output is ever
   reused between runs.
4. Generates a self-signed multi-SAN TLS certificate for `synthetic.auth006.internal`,
   `app.mystcrag.auth006.internal`, and `api.mystcrag.auth006.internal`; starts the
   in-process synthetic OIDC provider (HTTPS issuer + HTTP admin control plane) and the
   strict-allowlist browser CONNECT relay.
5. Builds the backend production bundle (`apps/backend/build.mjs`) in the run-scoped
   checkout and starts it with `node dist/index.js`.
6. Builds the frontend (`next build`) in the run-scoped checkout and starts it with
   `next start` (NODE_ENV=test, so loopback HTTP app origins are legal while the
   production server runtime is exercised).
7. Starts the **production topology** (scenario I): TLS reverse proxies expose the same
   backend and a second frontend instance (NODE_ENV=production) on real HTTPS synthetic
   DNS origins, proving the `__Host-` session cookie contract.
8. Runs specs A–I serially (one worker, `retries: 0` — flakiness must surface, never be
   absorbed).
9. `globalTeardown` stops every process it started (PID ownership verified before any
   signal), verifies every owned port was released, drops + verifies gone the isolated
   database, redacts credential-bearing header values from retained trace archives, and
   scans every retained artifact for leaked secrets/tokens/cookies. Any failure fails
   the run. A failed setup still tears the stack down, and a cleanup failure alongside a
   setup failure propagates as an `AggregateError` carrying both errors. Spec-spawned
   extra children are persisted as durable records the moment they are spawned — and if
   that registration fails, the child is reclaimed (SIGTERM → SIGKILL, exit awaited)
   before the failure surfaces, so a failed registration never leaks a live process or
   a bound port.

Every generated byte (logs, TLS material, run-state, build outputs, test-results,
traces, screenshots) lives only under `output/playwright/auth-006/<runId>/`, which is
already covered by the repository `.gitignore` rule `output/playwright/`.

## Repeatability gate

Run the suite twice from clean resources (two invocations, nothing reused in between —
each invocation creates its own database, ports plan, provider, build checkout, and
processes):

```bash
pnpm exec playwright test --config tests/auth-e2e/playwright.config.mts   # RUN 1
pnpm exec playwright test --config tests/auth-e2e/playwright.config.mts   # RUN 2
```

Both must pass. There is no retry configuration anywhere in the gate.

## Prerequisites

- Node 22+ and pnpm with an installed frozen lockfile (`pnpm install --frozen-lockfile`).
- A reachable PostgreSQL 16+ **with the `pgvector` extension available** (migrations require
  it). The admin connection is resolved from, in order: `AUTH006_DATABASE_ADMIN_URL`,
  `DATABASE_URL` (rewritten to its `/postgres` database), or
  `postgresql://$USER@localhost:5432/postgres`. The account needs `CREATEDB` rights.
- `openssl` on PATH (generates the multi-SAN synthetic topology certificate).
- Playwright 1.62.1 browsers installed (`pnpm exec playwright install chromium`).

## Port plan (offset applies to all)

| Port | Use |
| --- | --- |
| 18443 | Synthetic provider TLS issuer (`https://synthetic.auth006.internal/`) |
| 18444 | Provider admin control plane (loopback HTTP, Bearer token) |
| 18445 | Browser CONNECT relay (strict allowlist: `synthetic.auth006.internal:443` → 18443 only) |
| 18446 | Production-topology app TLS reverse proxy (`https://app.mystcrag.auth006.internal/`) |
| 18447 | Production-topology backend TLS reverse proxy (`https://api.mystcrag.auth006.internal/`) |
| 18450 | Backend under test |
| 18460 | Frontend under test (NODE_ENV=test) |
| 18461 | Production-topology frontend (NODE_ENV=production, behind the TLS proxy) |
| 18451 / 18470 | Reserved for the G-scenario negative backend/frontend spawns |

The synthetic issuer must be a canonical HTTPS DNS hostname with no port (the Auth0 SDK
and both issuer validators reject ports, IPs, and loopback). Non-root processes cannot
bind 443, so traffic to `synthetic.auth006.internal:443` is remapped:

- Browser: Playwright launch proxy → CONNECT relay on 18445. The relay accepts ONLY
  `CONNECT synthetic.auth006.internal:443`, verifies the ClientHello SNI equals the
  CONNECT host, and pipes everything else nowhere (403 refusal, counted; plain HTTP on
  the proxy port answers 405). The SNI parser demands EXACT consumption of every
  sub-vector — the extensions block must end exactly at the ClientHello handshake end,
  the server-name list must consume its extension entirely, and every list entry must
  be a single well-formed printable-ASCII host_name (duplicate, zero-length, truncated
  or trailing bytes are all malformed) — so no forged or malformed hello ever reaches
  the upstream.
- Node runtimes (BFF + backend): `NODE_OPTIONS=--require node-connect-preload.cjs`
  rewrites the connect() destination; TLS still verifies the synthetic hostname via
  `NODE_EXTRA_CA_CERTS`.

The production-topology origins are remapped instead of proxied: the browser rewrites
`app.mystcrag.auth006.internal` / `api.mystcrag.auth006.internal` to 127.0.0.1 via
`--host-resolver-rules` (bypassed from the proxy), and the production BFF reaches the
backend's HTTPS origin through the preload's `AUTH006_API_REMAP_HOST` rewrite (host →
127.0.0.1, port preserved — TLS end-to-end with the multi-SAN certificate).

## Failure evidence in CI

When the gate fails in CI, a dedicated sanitizer step (`scripts/sanitize-evidence.mjs`,
id `sanitize_auth006`) copies ONLY allowlisted, scanned file types from the raw run
directory into a separate `auth-006-sanitized/` directory. TLS material (`.pem`/`.key`,
the whole `tls/` tree) is never copied; the run-scoped build checkout (`work/`) is never
copied; symbolic links in the source tree are never read through (fail closed, reported
as a violation). Credential material in a path or NAME is scanned FIRST, before any
directory/extension decision, so a secret-bearing `token-<secret>.bin` (or a file inside
`tls/`) is a VIOLATION rather than a silently excluded entry. Only `.log .json .txt .md
.zip` are allowlisted — binary image types (`.png` and friends) are NOT: their content
cannot be reliably proven free of credential material, so they are never uploaded
unscanned (screenshots inside zip trace archives are covered, because every zip entry is
scanned on its RAW bytes — NUL bytes or binary content never skip the scan). Credential
material is scanned in file CONTENTS, in file/zip-entry NAMES, and in every zip entry
BEFORE anything is copied; each file is opened once with `O_NOFOLLOW` and, after the
open, the descriptor itself is proven to live inside the canonical source root (Linux:
the kernel-resolved `/proc/self/fd/<fd>` path; every platform: each ancestor segment is
verified to be a real directory and the descriptor's `fstat` identity must match the
verified path) so a mid-run ancestor-directory symlink swap can never redirect a read
outside the root; the CLI's stdout/stderr and the published `sanitize-summary.json` are
path-free (opaque references and sanitized categories only). The sanitized tree is built
in a staging directory and published with one atomic rename only after a zero-violation
scan — a failing scan publishes nothing at all. The artifact upload step is double-gated
(`failure() && steps.sanitize_auth006.outcome == 'success'`), so a failing sanitizer can
never publish a partial sanitized directory.

## Failure recovery

If a run crashed without teardown, the next invocation fails fast on the occupied port
plan (the suite never kills processes it did not start). Recover by hand:

```bash
# Find and stop stale AUTH-006 processes (ports 18443–18470 by default)
lsof -nP -iTCP:18443-18470 -sTCP:LISTEN

# Drop the orphaned database (name always matches mystcrag_auth006_<runid>_test)
psql -d postgres -c 'SELECT datname FROM pg_database WHERE datname LIKE $$mystcrag\_auth006\_%\_test$$;'
psql -d postgres -c 'DROP DATABASE "mystcrag_auth006_<runid>_test";'
```

Or set `AUTH006_PORT_OFFSET` and let the stale run coexist while it is investigated.

| `specs/i-production-secure-cookie.spec.mts` | I — positive production proof: `__Host-` session cookie contract on a real HTTPS origin, JS unreadability, session restore, protected call through the production BFF → HTTPS → backend chain, and direct Origin/CSRF mutation enforcement (correct origin creates state; missing and attacker origins are rejected 403 with no side effects) |
