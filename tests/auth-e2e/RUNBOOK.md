# AUTH-006 — Isolated Authentication Security & Full-Loop E2E Gate

TASK-AUTH-006. Owner: QA / GLM. Branch: `task/auth-006-security-e2e`.

This directory is a self-contained Playwright gate that proves the integrated real behavior
of AUTH-003 (BFF session), AUTH-004 (backend Auth0 access-token verification), and
AUTH-005 (frontend session integration) against the **unmodified production build** of
both runtimes.

## One command = one clean run

From the repository root:

```bash
pnpm exec playwright test --config tests/auth-e2e/playwright.config.ts
```

A single invocation performs the full lifecycle:

1. `globalSetup` resolves a unique run id and asserts the port plan is free.
2. Creates an isolated PostgreSQL database `mystcrag_auth006_<runId>_test` (name pattern
   is asserted before any `CREATE`/`DROP`), runs `prisma migrate deploy` and the standard
   seed against it.
3. Generates a self-signed TLS certificate for `synthetic.auth006.internal` and starts the
   in-process synthetic OIDC provider (HTTPS issuer + HTTP admin control plane) and the
   browser CONNECT relay.
4. Builds the backend production bundle (`apps/backend/build.mjs`) and starts it with
   `node dist/index.js`.
5. Builds the frontend (`next build`) and starts it with `next start` (NODE_ENV=test, so
   loopback HTTP app origins are legal while the production server runtime is exercised).
6. Runs specs A–G serially (one worker, `retries: 0` — flakiness must surface, never be
   absorbed).
7. `globalTeardown` stops every process it started, drops the isolated database, and scans
   every retained text artifact for leaked secrets/tokens/cookies.

Every generated byte (logs, TLS material, run-state, test-results, traces, screenshots)
lives only under `output/playwright/auth-006/<runId>/`, which is already covered by the
repository `.gitignore` rule `output/playwright/`.

## Repeatability gate

Run the suite twice from clean resources (two invocations, nothing reused in between —
each invocation creates its own database, ports plan, provider, and processes):

```bash
pnpm exec playwright test --config tests/auth-e2e/playwright.config.ts   # RUN 1
pnpm exec playwright test --config tests/auth-e2e/playwright.config.ts   # RUN 2
```

Both must pass. There is no retry configuration anywhere in the gate.

## Prerequisites

- Node 22+ and pnpm with an installed frozen lockfile (`pnpm install --frozen-lockfile`).
- A reachable PostgreSQL 16+ **with the `pgvector` extension available** (migrations require
  it). The admin connection is resolved from, in order: `AUTH006_DATABASE_ADMIN_URL`,
  `DATABASE_URL` (rewritten to its `/postgres` database), or
  `postgresql://$USER@localhost:5432/postgres`. The account needs `CREATEDB` rights.
- `openssl` on PATH (generates the synthetic issuer certificate).
- Playwright 1.62.1 browsers installed (`pnpm exec playwright install chromium`).

## Environment variables (all optional)

| Variable | Default | Meaning |
| --- | --- | --- |
| `AUTH006_RUN_ID` | random `r<time><rand>` | Pins the run id (used in database name, output directory, log names). Must match `[a-z0-9]{1,40}`. |
| `AUTH006_DATABASE_ADMIN_URL` | derived from `DATABASE_URL` | Admin connection used to create/drop the isolated database. |
| `AUTH006_PORT_OFFSET` | `0` | Shifts the whole port plan (0–10000) to allow parallel isolated runs. |
| `AUTH006_ACCESS_TOKEN_LIFETIME` | `12` | Synthetic provider access-token lifetime in seconds (specs B/C rely on the short default). |
| `AUTH006_CLIENT_SECRET` / `AUTH006_SESSION_SECRET` / `AUTH006_ADMIN_TOKEN` | random per run | Secrets are generated in memory when absent; they are never written to disk or logs. |

## Port plan (offset applies to all)

| Port | Use |
| --- | --- |
| 18443 | Synthetic provider TLS issuer (`https://synthetic.auth006.internal/`) |
| 18444 | Provider admin control plane (loopback HTTP, Bearer token) |
| 18445 | Browser CONNECT relay (maps `synthetic.auth006.internal:443` → 18443) |
| 18450 | Backend under test |
| 18460 | Frontend under test |
| 18451 / 18470 | Reserved for the G-scenario negative backend/frontend spawns |

The synthetic issuer must be a canonical HTTPS DNS hostname with no port (the Auth0 SDK
and both issuer validators reject ports, IPs, and loopback). Non-root processes cannot
bind 443, so traffic to `synthetic.auth006.internal:443` is remapped:

- Browser: Playwright launch proxy → CONNECT relay on 18445.
- Node runtimes (BFF + backend): `NODE_OPTIONS=--require node-connect-preload.cjs`
  rewrites the connect() destination; TLS still verifies the synthetic hostname via
  `NODE_EXTRA_CA_CERTS`.

## Production bundle runtime restoration (pre-existing main gap)

`node apps/backend/dist/index.js` currently fails at import time on main baseline
`4cac24c`: crawlee entered the backend import graph in `f3dd030` (2026-08-21) — after the
runnable-artifact fix `66b2a89` (2026-07-22) — and two of its transitive modules call
`require.resolve` at module scope (`jquery`, and jsdom's `./xhr-sync-worker.js`), which
esbuild cannot inline. The gate restores the intended lookups from the harness without
touching backend sources:

- `NODE_PATH` → pnpm's hoisted store (`node_modules/.pnpm/node_modules`) for bare
  specifiers.
- `dist/xhr-sync-worker.js` symlink → the real jsdom worker asset, created after every
  backend build.

Both restorations are documented in `fixtures/stack.ts` and in the evidence report. The
bundle itself is built from unmodified sources by the unmodified `build.mjs`.

## Failure recovery

If a run crashed without teardown, the next invocation fails fast on the occupied port
plan (the suite never kills processes it did not start). Recover by hand:

```bash
# Find and stop stale AUTH-006 processes (ports 18443–18470 by default)
lsof -nP -iTCP:18443-18470 -sTCP:LISTEN

# Drop the orphaned database (name always matches mystcrag_auth006_<runid>_test)
psql -d postgres -c 'SELECT datname FROM pg_database WHERE datname LIKE $$mystcrag\_auth006\_%\_test$$;'
psql -d postgres -c 'DROP DATABASE "mystcrag_auth006_<runid>_test";'
```

Or set `AUTH006_PORT_OFFSET` and let the stale run coexist while it is investigated.

## What the specs cover

| File | Scenario group |
| --- | --- |
| `specs/a-identity-lifecycle.spec.ts` | A — first login, ExternalIdentity↔User mapping, stable actor on re-login, concurrent login, subject never becomes actorId |
| `specs/b-session-lifecycle.spec.ts` | B — encrypted HttpOnly cookie session, refresh persistence, rolling idle expiry, absolute expiry, cookie attributes, no token leakage |
| `specs/c-logout-expiry.spec.ts` | C — POST/GET logout semantics, Origin enforcement, idempotent logout, idle/absolute expiry, refresh failure, provider outage fail-closed |
| `specs/d-protected-business-loop.spec.ts` | D — real protected design/tarot/order loop end-to-end |
| `specs/e-two-user-isolation.spec.ts` | E — two-user data and session isolation |
| `specs/f-responsive-accessibility.spec.ts` | F — desktop/mobile viewports, keyboard operability, touch targets, aria contracts |
| `specs/g-configuration-negatives.spec.ts` | G — production config negatives, signed-test refusal, issuer/URL/secret validation, JWKS outage fail-closed |

Evidence retention follows `docs/governance/QA_EVIDENCE_RETENTION.md`: traces and
screenshots are `retain-on-failure`/`only-on-failure`; a passing run keeps only logs and
run-state under the run directory.
