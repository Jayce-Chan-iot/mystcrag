## 3. Isolation properties of the gate

One command — `pnpm exec playwright test --config tests/auth-e2e/playwright.config.ts` — is one complete clean run:

- unique run id → unique database `mystcrag_auth006_<runId>_test` (name pattern asserted before any `CREATE`/`DROP`), `prisma migrate deploy` + standard seed against it;
- unique port plan (18443/18444/18445/18450/18460 + 18451/18470 for negative spawns), asserted free before start;
- self-signed TLS cert for `synthetic.auth006.internal`, in-process synthetic OIDC provider (HTTPS issuer, HTTP admin control plane), browser CONNECT relay and `node:net` connect() preload to remap the port-443 issuer;
- backend and frontend built from **unmodified sources** by the unmodified build pipelines and started as production runtimes;
- all secrets (client secret, session secret, admin token) generated in memory per run, never written to disk or logs;
- teardown stops only processes it started, drops only its own database, redacts credential-bearing headers from retained trace archives, and scans every retained artifact for the run's secrets plus token/cookie leakage patterns (including decompressed trace content) — any hit fails the run.

Nothing from a developer machine is reused: no dev server, no dev database, no shared `.next`, no pre-seeded browser state, no production Auth0 tenant. Test order independence is enforced by serial execution (`workers: 1`) with per-test synthetic identities.

## 7. Blocking production defect — authenticated mutations 500 in the production build

### Symptom (deterministic, both runs)

Every authenticated **non-GET** request to `/api/**` through the BFF returns:

```json
500 {"error":{"code":"INTERNAL_ERROR","message":"Session service unavailable.","requestId":"…"}}
```

Observed requestIds: RUN 1 — `39fbb3f7-58cf-4817-acb4-e58f74ffc6b5` (D1), `7427675b-133b-481f-ae1b-6e167d884f82` (E1); RUN 2 — `4d49b36a-5221-4eb9-8fc8-eae99766851c` (D1), `9c1dc985-1530-49dd-9df8-c0f92d5c4f8c` (E1). Each is corroborated by a privacy-safe `auth.dependency_failed` event in the frontend server log of its run.

### Root cause chain (all code on baseline `main`, quoted from the worktree)

1. `apps/frontend/src/features/auth/server/bff.ts` (step 3, lines 278–282): for mutations the BFF reads the body — `body = await request.text()` — which **consumes/disturbs the request's body stream**.
2. `bff.ts` (step 4, line 290): `await deps.touchSession(request)` then triggers the SDK's real passive session rolling — `getAuth0Client().middleware(request)` in `apps/frontend/src/features/auth/server/auth0-server.ts`.
3. `@auth0/nextjs-auth0@4.27.0` `dist/server/client.js` (`middleware`): `const nextReq = toNextRequest(req); …`
4. `dist/server/next-compat.js` (`toNextRequest`):
   ```js
   if (input instanceof NextRequest) { return input; }
   …
   return new NextRequest(input.url, { …, body: input.body, duplex: input.duplex ?? "half" });
   ```
5. Under the **Next.js 16 Turbopack production build**, the app chunk and the SDK chunk resolve **different module instances of `next/server`**, so `input instanceof NextRequest` is `false` even though the object is a `NextRequest`. (Confirmed during this task's diagnosis by instrumenting the SDK in `node_modules`; dev-mode webpack has a single instance, which is why dev works.)
6. The fallback therefore **reconstructs** the request from the already-consumed stream → `TypeError: Response body object should not be disturbed or locked`.
7. The throw propagates out of `touchSession` into the catch at `bff.ts` lines 291–298 → the observed `500 "Session service unavailable."`.

### Why this is a production defect, not a test artifact

- The gate builds the frontend from **unmodified sources** with the repository's own `next build` and runs `next start`; no source, dependency, or build configuration was altered by AUTH-006.
- GET requests through the same BFF succeed (no body read → SDK reconstruction of an unconsumed stream succeeds), which is exactly why 30 of 32 scenarios pass and only the mutation-driven D1/E1 fail.
- The failure is byte-identical across two fully isolated clean runs on two freshly created stacks.

### Blast radius on baseline `main`

All authenticated mutations proxied by the BFF in the production build: design generate/save/clone/update/delete, order creation from a design, and tarot mutations — i.e., the entire write surface of the product is non-functional in production while logins, sessions, logout, and reads work. The gate is the first suite in the repository that drives authenticated mutations through the real production BFF, which is why this survived earlier task-level verification (unit tests call `handleBffRequest` with already-materialized request doubles and never cross the Turbopack chunk boundary).

### Recommended remediation (owner: Frontend Agent — **not performed by QA**, `apps/frontend/**` is outside this task's writable paths)

Any one of:
1. **Minimal seam (recommended):** in `bff.ts`/`auth0-server.ts`, stop handing the SDK the request whose body was already consumed — e.g. run rolling first and/or pass `touchSession` a `NextRequest` reconstructed from the cached body text (fresh stream), so the SDK's cross-chunk reconstruction path succeeds.
2. Ensure a single `next/server` module instance across chunks (bundler aliasing / `serverExternalPackages` for the SDK).
3. Track/upgrade the upstream SDK if the Turbopack chunk-duplication behavior is fixed there.

This is **not** the `AUTH006_BLOCKED_TESTABILITY_SEAM` case: the harness needs no production seam to run — it runs the production build as-is and has caught a real defect. The block is the defect itself.
