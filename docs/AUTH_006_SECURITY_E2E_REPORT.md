## 3. Isolation properties of the gate

One command — `pnpm exec playwright test --config tests/auth-e2e/playwright.config.mts` — is one complete clean run:

- unique run id → unique database `mystcrag_auth006_<runId>_test` (name pattern asserted before any `CREATE`/`DROP`), `prisma migrate deploy` + standard seed against it;
- unique port plan (18443/18444/18445/18446/18447/18450/18460/18461 + 18451/18470 for negative spawns), asserted free before start and verified released at teardown;
- run-scoped build checkout: `apps/backend` and `apps/frontend` are copied into `output/playwright/auth-006/<runId>/work/apps/` and every build and start runs INSIDE that copy — the developer workspace's `.next`/`dist` is never read, and **no build output is ever reused between runs**;
- self-signed multi-SAN TLS certs for `synthetic.auth006.internal`, `app.mystcrag.auth006.internal`, `api.mystcrag.auth006.internal`; in-process synthetic OIDC provider (HTTPS issuer, HTTP admin control plane); browser CONNECT relay and `node:net` `connect()` preload to remap the port-443 issuer; TLS reverse proxies for the production HTTPS topology;
- backend and frontend built from **unmodified sources** by the unmodified build pipelines and started as production runtimes (`next start`, `node dist/index.js`);
- a fixture-level regression assertion enforces the production config contract `MYSTCRAG_AUTH_CALLBACK_URL === MYSTCRAG_APP_ORIGIN + '/auth/callback'` before any process starts, and readiness requires the production-topology frontend's auth configuration to actually resolve (`/auth/session` answers authenticated JSON) — a Proxy fail-closed page can never be mistaken for "ready";
- all secrets (client secret, session secret, admin token) generated in memory per run, never written to disk or logs;
- teardown stops only processes it started — live `ChildProcess` handles are kernel-verified, and pids recovered from run-state.json are verified against the CURRENT command line AND the run-scoped working directory before any signal — verifies every owned port was released, drops and verifies gone its own database, redacts credential-bearing headers from retained trace archives, and scans every retained artifact for the run's secrets plus token/cookie leakage patterns (including decompressed trace content). Any hit fails the run.
- a failed setup still tears the stack down, and when that cleanup fails too, BOTH errors propagate as one `AggregateError` (repair #3 below) — leftover resources can never hide behind the setup error.

Nothing from a developer machine is reused: no dev server, no dev database, no shared `.next`, no pre-seeded browser state, no production Auth0 tenant. Test order independence is enforced by serial execution (`workers: 1`, `retries: 0`) with per-test synthetic identities.

Narrow-regression run: `rmtdlqs3ez04iacui96` — **11/11** (H1–H8 incl. H4b/H5b, I1), stack booted by the normal global setup and torn down cleanly.

Two harness defects were found and fixed in an earlier round while closing the H3 regression, both in the relay's tunnel gate (never in allowlist semantics):

1. **Partial-record parsing** — a ClientHello split across TCP segments was parsed as "not a hello" and destroyed a legitimate tunnel; the gate now buffers until the 5-byte record header declares the record complete.
2. **Listener-gap race** — tunnel bytes pipelined right behind the CONNECT head could fire a `data` event between head consumption and gate arming, with no listener registered (flowing mode silently discards them). The relay now `pause()`s the socket the moment the head is parsed and `resume()`s it only after the SNI gate is armed, so no byte can ever be lost in that gap. H3 exercises exactly this pipelining shape, which is why the real-browser flow (always waits for the 200) never exposed it.

### D1 evidence (protected business loop)

The full authenticated loop works end to end on the unmodified production build: login → design generation → save → list → reload/fetch → tarot session → selection → reveal → order creation (revision/pricing/total verified) → order listing → logout, with every step passing through the real BFF (`Origin`/CSRF enforcement + access-token verification) to the real backend, and dying cleanly at logout (protected API answers 401, the UI shows the `UNAUTHORIZED` error surface and the login button again).

### E1 evidence (two-user isolation)

Two synthetic users in two separate browser contexts. B's projections list none of A's designs or orders. For every owner-scoped operation — design read, save, clone, update, delete, order-from-design, Tarot session read and select — B's response for A's (foreign) resource and for a nonexistent resource is compared directly: identical HTTP status AND identical stable error code (both surface as 403 `FORBIDDEN`), so no existence/ownership oracle leaks. Operations that are not owner-scoped by product design (design generation, catalog) claim no such comparison. After all of B's attacks, A's state is re-read and asserted unchanged: design revision, Tarot session revision and status, the order projection's exact count and the original order's contents (status, currency, totalAmountMinor, createdAt, designId); B's order projection remains exactly zero. No session/token/profile material crosses between contexts (separate cookie jars and storage, DB ownership asserted, distinct internal actors).

### I1 evidence (production Secure Cookie)

On the production HTTPS origin (`https://app.mystcrag.auth006.internal:<appTls>`, valid multi-SAN cert, synthetic DNS, `NODE_ENV=production`, production config validator engaged):

- cookie name is exactly `__Host-mystcrag_session`; no legacy `mystcrag_session` and no chunked `__Host-mystcrag_session__*` cookies exist;
- `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, host-only (no `Domain` attribute, never a parent domain);
- `document.cookie` cannot read the session credential; no credential value in `localStorage`/`sessionStorage`;
- a fresh navigation in the same context restores the authenticated session (session restore after reload), still on the same `__Host-` cookie;
- `/auth/session` answers `200` with `"authenticated":true` and the protected `/api/designs` answers `200` through the production BFF → HTTPS → backend chain (Origin/CSRF + access-token verification included).

- `tests/auth-e2e/package.json` does not exist in the candidate (ES modules are declared per-file via `.mts`/`.mjs`; no directory-local manifest).
- Retained run evidence lives only under `output/playwright/auth-006/<runId>/` (git-ignored): stack logs, run-state, failure-only traces/screenshots (none — all green), per-run TLS material and per-run build checkout.
- The CI artifact contract: ONLY the sanitized, explicitly allowlisted directory `output/playwright/auth-006-sanitized/` is ever uploaded (`actions/upload-artifact@v4`, failure-only, 7-day retention), and the upload step is additionally gated on the sanitizer step's own success. The sanitizer never copies TLS material (the whole `tls/` directory, `*.pem`, `*.key`, the provider private key by basename), never copies the run-scoped build tree (`work/`), considers only allowlisted extensions (`.log .json .txt .md .png .zip`), never reads or copies a symbolic link (fail closed, recorded as a violation), scans every text file, every file NAME/relative path, and every decompressed zip entry name and body for credential material BEFORE copying, builds the sanitized tree in a staging directory, and publishes it with one atomic rename only after a zero-violation scan. A failing scan — or a failing sanitizer — publishes nothing at all, and the CI upload gate skips the upload. No raw trace, TLS private key, or credential-bearing file can reach the upload directory; on passing runs (like both clean rounds here) nothing is uploaded at all.

## 9. Residual risks and current limitations

1. **No real external Auth0 tenant is exercised.** The OIDC counterparty is the in-process synthetic provider (correct discovery document, JWKS-backed signed tokens, PKCE, code exchange, refresh). Real-tenant behaviors this cannot prove: tenant-side rate limiting/outage semantics beyond the simulated G7 outage, Auth0-specific login page markup, and real-tenant clock skew/JWKS rotation cadence. The SDK, validators, and every production code path under test are the real ones; only the wire counterparty is synthetic. A real-tenant smoke run remains future work outside this task's scope.
2. **CI has not yet executed on a GitHub runner.** The workflow (including the new double-gated upload) is verified by the static H8 regression and by inspection; `steps.<id>.outcome` semantics follow documented GitHub Actions behavior. Local runs used Node 26 vs CI's Node 22 — both are supported runtimes for Playwright 1.62.1 and Next.js 16.
3. The run-scoped cwd verification of recovered pids was exercised locally on macOS (`lsof`); the Linux branch (`/proc/<pid>/cwd` readlink) will first execute on the GitHub runner.
4. Local PostgreSQL is 17.10 while CI pins pgvector/pgvector:pg16 — migrations passed on both major versions' required surface (17 locally, 16 via the earlier repository baselines).
5. The backend production-bundle runtime restorations (`NODE_PATH` to pnpm's hoisted store for `require.resolve("jquery")`, and the `xhr-sync-worker.js` symlink) compensate a pre-existing main gap documented in `tests/auth-e2e/RUNBOOK.md`; they are harness-side only and touch no tracked file.
