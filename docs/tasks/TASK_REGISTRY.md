Scope: the Backend production bundle (`apps/backend/dist/index.js` via `apps/backend/build.mjs`) inlines crawlee/playwright/jsdom through the knowledge-core → knowledge-ingestion chain. Three runtime lookups fail under a clean `pnpm production` dependency layout: crawlee's `playwright-utils.js` resolves `"jquery"` at module scope and jsdom's `XMLHttpRequest-impl.js` resolves its sibling `"./xhr-sync-worker.js"` — both calls esbuild cannot inline — and sharp's eager `@img/sharp-*` native binding load, which esbuild's conservative side-effect analysis keeps even though the backend imports only sharp-free asset-pipeline symbols (`detectAssetSourceKind`, `sha256OfBytes`, `ArchiveStore`, `ArchiveStoreError`). The artifact must therefore start directly with no `NODE_PATH`, no test harness, and no manual/absolute path or symlink. Preferred approach: a portable explicit `jquery` dependency, a build-time copy of the required jsdom `xhr-sync-worker.js` runtime asset (bundled self-contained, not a symlink), and marking `sharp` side-effect-free so esbuild tree-shakes the dead image-processing chain out of the API bundle. No machine path may be written into the artifact; do not copy the entire `node_modules`; do not upgrade Crawlee/Playwright/Next; do not change business logic.
