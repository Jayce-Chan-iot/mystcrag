# DIY 工作台最多 60 颗珠子：设计规格

**任务：** `TASK-UX-DIY-CAP-SPEC-001`
**日期：** 2026-10-10
**状态：** 产品所有者已确认口径；本文待书面审阅，尚未授权运行时代码实施

## 1. 目标和范围

DIY 工作台允许用户自由搭配，但一份可继续新增的设计最多包含 **60 颗物理珠子**。在上限处给出清楚反馈，服务端也拒绝绕过界面的第 61 颗。此限制是 DIY 的组成规则，不是腕围适配建议，不能通过视觉压缩、只禁用按钮或更改材料长度代替。

计数采用已验证的 `DesignV1.beads.length`，与 `bracelet.totalBeadCount` 一致。每个 `BEAD` 组件计一颗；`INLINE` 隔珠、连接件和 `ANCHORED` 挂饰等配饰不计数。替换同一颗珠子的材质/直径、移动顺序不增加计数；全新空托盘到首颗珠子的创建不受影响。价格、库存、修订、所有权和订单仍由原有权威流程决定。

本规则只约束进入 DIY 后的新增及后续完成，不在通用 `DesignV1Schema` 加 `.max(60)`，不拒绝读取已有或其他来源的合法设计，不改 AI/Tarot/Oracle 的生成协议，也不改变 Bracelet Engine 几何或 47% 托盘边界。若后续产品决定所有生成模式也限 60，须另立任务。

## 2. 选择的方案与边界

选择“共享公开规则常量 + 服务端权威校验 + 前端即时引导”。`CONTRACT` 先声明唯一的 DIY 珠数上限 `60`（不改 DesignV1/Update DTO 的结构），`BACKEND` 在现有设计更新和完成边界使用该规则，`FRONTEND` 消费同一常量做即时提示与禁用。超限需有可识别的公开错误码，这是 API 错误契约的增量而非 DesignV1 Schema 上限。后端仍负责最终判定；前端不能靠自己的当前数字替代服务器快照。

未采用仅前端禁用：直接 API、过期页面和并发请求仍可加入第 61 颗。未采用通用设计 Schema 上限：那会令超过 60 颗的历史快照、订单和非 DIY 推荐在读取时失效。也不把 60 写进 Bracelet Engine：几何内核必须继续接受合法的输入长度，供历史数据和其他消费者使用。

## 3. 服务端规则

1. 对一个更新请求按现有顺序应用完整 `operations` 后，以最终 `beads.length` 判定。对当前不超过 60 的设计，最终数不得超过 60；`60 → 60` 的换珠/移动/删后再加合法，`60 → 61` 失败。请求失败时不写新修订、价格、库存保留或事件；保持当前已保存设计和 `expectedRevision` 的原有冲突保护。
2. 对既有超过 60 颗的设计，允许读取并逐次**减少**珠数（例如 `70 → 69 → … → 60`），也允许移动已有珠子、替换同一颗珠子的材料和调整配饰；只要当前仍超限，任何新增珠子的操作都拒绝，即使同一批次另有删除。已经超过上限的状态不能被新规则解释为 404、损坏数据或他人设计。保存已有状态可以继续用于恢复，但新的完成/订单请求须先降至不超过 60；既有订单快照不回写、不撤销。
3. 同一批操作里的配饰增删不改变珠数上限判定。`REPLACE_COMPONENT` 从配饰改为珠子时按最终珠数处理；同一组件换 SKU 不增加颗数。连续快速添加、离线重试和两个并发标签页都按服务端当前修订及最终数量决定；不能出现两次成功把 60 变 62。
4. 超限拒绝使用现有安全错误封套，新增稳定业务错误码 `DIY_BEAD_LIMIT_EXCEEDED`，HTTP 400；前端可据此显示“每份 DIY 设计最多 60 颗珠子，请先移除一颗再添加”。该码必须同时加入服务端错误枚举、前端已知服务端码和三语错误呈现，不能降级成泛化的 `VALIDATION_ERROR` 或 `NETWORK_ERROR`。不暴露库存、成本或其他用户设计。重复请求仍遵守原有幂等与冲突语义。

## 4. 前端体验

- 珠数处显示 `当前数量 / 60`，到 60 时材料卡的“加入”动作禁用或明确拦截，并用文字说明原因；材料浏览、换珠、移动、删除、配饰操作保持可用。键盘和屏幕阅读器能读到限制及状态，不只靠灰色表达。
- 乐观编辑与待同步队列须考虑已提交和排队中的添加：快速连点不能在界面上临时排出第 61 颗。若服务器返回超限、冲突或重试失败，恢复最后确认的设计并给出可执行的提示，不虚报成功或新价格。
- 旧设计超过 60 时显示明确的“还需移除 N 颗”提示，允许逐颗删减；新增不可用。保存可用于保护旧设计，完成操作在降到 60 前不可用。状态文案按现有 `zh-CN`、`zh-TW`、`en-US` 语言机制提供，不改变货币或设计内容。
- 全新草稿仍是零珠空托盘；第 1 颗才经现有首珠 API 创建，60/61 边界不能破坏首珠幂等、历史设计选择或所有者校验。

## 5. 几何展示与当前手串任务的关系

`TASK-UX-BRACELET-FE-001` 仍拥有共享展示投影，只能按自身已登记路径修复和验收。60 颗上限不等于准许把任意合法 `PublicDesignV1` 的展示算法悄悄改为最多 60：历史设计和非 DIY 结果预览仍可能携带更多珠子。若产品决定这些路径也不展示超限设计，须明确另行变更。当前求解器对 160 颗输入的错误“无解”结论不能通过删除回归或只在前端截断数组来伪装成修复；可在独立任务验收时明确其输入保证与降级呈现规则。

## 6. 实施依赖和归属

1. `SOL` 登记精确任务与路径；`CONTRACT` 任务先提供公共政策常量和契约文档，不变更 DesignV1 或 UpdateDesign 的请求/成功响应结构；错误封套枚举须按第 3 节增量扩展。后端、前端任务只在该合同落地后开始。历史文件的 `.test.ts` / `.test.tsx` 登记错误由单独的治理修订处理，不授权执行者改任务注册表。
2. `BACKEND` 任务修改 `apps/backend` 中设计更新与完成边界、对应单元/路由测试，并同步 API、交互验收文档中与完成条件冲突的表述。不得改 Prisma、生成器或第三方设计来源。
3. `FRONTEND` 任务修改 DIY 数量展示、添加行为和三语文案及相邻测试；保留桌面三区、手机上托盘下材料区布局，不碰价格/库存/修订权威或 Bracelet Engine。
4. `QA` 任务用真实服务端与两名用户复测 59/60/61、快速连点、并发修订、旧设计删减、保存/完成、三语/键盘/手机；另核对现有订单不可变。独立视觉证据必须注明设备视口和源版本。

## 7. 验收矩阵

| 场景 | 预期 |
| --- | --- |
| 59 颗加一颗 | 成为 60，服务端确认的修订/价格更新一次 |
| 60 颗再加一颗 | 前端明确提示；直接 API 也拒绝；持久化仍为 60 |
| 60 颗换珠、移动、增删配饰 | 珠数仍为 60；原有流程可用 |
| 同批删一颗再加一颗 | 最终 60，按现有操作顺序、价格和修订规则处理 |
| 59 颗快速双击、跨标签并发 | 不出现已保存的 61 颗；失败可恢复、无重复修订 |
| 旧设计 70 颗 | 能打开与逐次移除；不能新增；降到 60 前不能新完成，既有订单不变 |
| 空托盘/首珠 | 仍先零珠；首珠创建一次且只得到当前用户设计 |
| 三语和无障碍 | 数量、上限、拒绝原因和下一步均可读；无横向溢出或死按钮 |
